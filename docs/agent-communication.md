# Agent 间通信：调研笔记

- 主题：双 agent 交流能否用更高效、更精确的编码替代自然语言？
- 初稿：echo2（2026-10-20）
- 复核：echo1（2026-10-20，独立打开原文核对数字与结论）
- 结论先行：**保留自然语言正文，只用结构化信封做路由与去重；不要自造紧凑 DSL。**

## 1. 三条外部证据

### 1.1 自然语言工具调用 vs 结构化调用

**The Remarkable Effectiveness of Providing AI Agents with Natural Language Tools: A Replication Study**（arXiv:2607.03953，2026-07）

- 14 个模型、8,560 次试验的复现研究。
- 自然语言工具调用准确率 **62.3%**，结构化 JSON 为 **47.4%**（校正后）；关键错误从 755 降到 51（**-93%**）。
- 自然语言方案 token 反而少 **25.2%**。
- 作者指出：结构化解析失败会触发重试、回退与协调开销，在递归 agent 工作流里被放大。
- 限制：模型能力会调节收益；对已经针对结构化调用重度优化的前沿模型，优势变小甚至反转。

**对我们的意义**：自定义紧凑编码不是免费的。省下的字节可能被解析失败和重试吃掉，而且双方模型都必须额外学习这套编码。

### 1.2 文件优先的 agent 协作协议

**tap: A File-Based Protocol for Heterogeneous LLM Agent Collaboration**（arXiv:2606.14445，2026-06）

- 消息以 **Markdown 正文 + YAML 元数据** 的文件形式落盘，文件是唯一可信来源。
- 双层通信：Tier 1 读文件（可恢复、可审计），Tier 2 实时通知（降低延迟）。
- 通知失败、接收方重启都不会丢消息，只会延迟；接收方收到通知后仍回读原文件。
- 27 天、37 代自举运行，209 个 PR、717 个运行工件。

**对我们的意义**：`logs/` 是 Tier 1，tmux `send-keys` 只是 Tier 2 的门铃。正文永远落盘，门铃丢了自己去读文件。

### 1.3 紧凑格式的代价

**Notation Matters: A Benchmark Study of Token-Optimized Formats in Agentic AI Systems**（arXiv:2605.29676，2026-05）

- 在 BFCL、MCPToolBenchPP、MCP-Universe、StableToolBench 四个基准、五个开源权重模型上评测 TOON / TRON。
- TRON 最多省 **27%** token，但准确率相对 JSON 最多掉 **14pp**。
- TOON 最多省 **18%** token，准确率约掉 **9pp**；多轮场景中解析失败会级联，并行工具调用输出在多数模型上崩溃。
- 作者的实用建议：紧凑格式只在“大量结构相似工具”的特定负载下值得，且必须实测，不能假设。

**对我们的意义**：连专门设计的 token 优化格式都要付出准确率代价；我们临时发明的 DSL 更不可能例外。

## 2. 设计结论

1. **正文用自然语言**：意图、理由、边界条件、反驳，全部留在 `body`。
2. **信封只放机器需要的字段**：`id`、`ts`、`from`、`to`、`type`、`reply_to`。不要为了“省 token”把语义压成缩写。
3. **文件是事实来源**：消息先写文件并原子发布（临时文件 + rename），再发 tmux 门铃。
4. **通知不是已读**：收到门铃后必须回读文件；`ack` 是显式动作，不靠“看到了”推断。
5. **可审计**：一条消息一个文件，失败时能定位到具体消息，不依赖解析整段日志。
6. **不追求字节数**：端到端延迟主要花在模型推理；优先降低漏消息、歧义和重复读全文。

## 3. 待验证

- 上述证据来自工具调用与异构 agent 场景，不完全等同于我们这种“共享文件系统 + 同模型家族”的对话。
- 需要本地小实验：同一组 20 条消息，比较“日志自然语言”与“信封 + 自然语言正文”的 token、唤醒到行动延迟、语义无损率、老板可读性。
- 实验脚本与结果应落到 `scripts/` 与 `reports/`，不要把结论只留在对话里。
