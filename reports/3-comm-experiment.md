# 20 消息通信对照实验（v0.1，附录）

日期：2026-10-20
目的：验证 task3 “邮箱默认采用”的代价与收益；不抢主调研任务。
设计：20 条**半合成**消息（8 INFO / 5 ASK / 4 ACK / 3 ERROR），每条含唯一事实（日期、数字、owner、路径、许可证等）。A 臂=日志散文（标题行 + 自然语言 body）；B 臂=同一 body 的邮箱 JSON（实验用 v0.3 格式；v0.4 仅重编码信封做开销对比）。两名**盲读者**（独立 subagent，仅见各自通道 + 20 题测验）分别回答；标准答案预先固定。语料已入库 `reports/3-comm-experiment-data/`（A/B 双臂、20 题、标准答案）；生成脚本在 `/tmp/opencode/comm_experiment/`（未入 git）。

## 结果

| 指标 | A 臂（日志散文） | B 臂（邮箱 JSON） | B vs A |
| --- | ---: | ---: | ---: |
| UTF-8 字节 | 4,222 | 6,375 | **+51.0%** |
| 近似 token* | 1,305 | 1,914 | **+46.7%** |
| 20 题盲测 | 20/20 | 20/20 | 持平 |
| 可行动子集（12 条 ASK/ACK/ERROR） | 2,567 B | 3,848 B | **+49.9%** |

\* 近似 token：CJK 字=1、英文/数字词=1.3、标点=0.5；只用于同口径比较，不是真实 tokenizer。

**还原质量**：两臂均 20/20；差异只在措辞（“48” vs “48 帧”、“5 行” vs “5 行以内”），语义无损。未发现邮箱格式导致的字段丢失或歧义。

**开销来源**：B 臂 body 合计 3,321 B，v0.3 信封约占 3,054 B（JSON key、id、ts、from/to/type、空 `reply_to`、缩进）；v0.4 紧凑化后信封约 2,334 B（仍占 body 的 70%）。也就是说，**邮箱的主要成本不是正文，而是每条消息重复的元数据**。

## 解释

1. **默认采用邮箱，不应被包装成“省 token”**。在 20 条消息的规模上，邮箱比日志散文多约 50% 字节/token；它的收益是路由、回执、去重、跨会话可靠唤醒，不是压缩。
2. **INFO/长文必须继续只写日志**。实验里 8 条 INFO 如果也走邮箱，纯属为路由付溢价；规范已写明 INFO 不用邮箱。
3. **可行动消息（ASK/ACK/ERROR）走邮箱是合理的**：12 条可行动消息的 +52% 开销，换来明确 `reply_to`/`ack`/失败重投；对双 agent 协作是保险，不是浪费。
4. **格式已优化**：`msg.py` v0.4 改为紧凑分隔符、空 `reply_to` 不写；同一语料 B 臂从 6,375 B/1,914 tok 降到 **5,655 B/1,828 tok**，开销从 +51.0%/+46.7% 降到 **+33.9%/+40.1%**（可行动子集 +33.1%/+38.6%），字段不丢。v0.4 只改信封，body 未变，故盲测 20/20 结论不变。
5. **未测项**：真实唤醒延迟、重复投递、ack 失败、老板可读性、20 条以上的长会话。当前只能支持“语义无损、开销可接受”的结论，不能支持“邮箱更快”。

## 建议

- 保持 task3 的“默认采用”：`ASK`/`ACK`/`ERROR` 默认邮箱；`INFO`/长文/背景只写日志。
- `msg.py` v0.4 已落地：紧凑 JSON + 省略空 `reply_to`；同语料实测 +33.9% 字节/+40.1% token；下次复测目标 ≤ +35% 字节。
- 20 条实验升级到 40 条时，再加入“实时唤醒延迟”和“重复投递”两个维度。
