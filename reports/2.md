## 结论与产出

1. **README 体系**（echo1 执笔、自查链接一致；`scripts/README.md` 由 echo2 随 `8e442a3` 落盘）：根 README 引导新会话快速进入状态；`tasks/`、`reports/`、`logs/`、`conventions/`、`docs/`、`scripts/` 六处目录说明各自回答"是什么、谁能动、文件生命周期"；目的是后来者（或 boss）五分钟看懂目录职责。
2. **交流效率调研结论**（锚点：`docs/agent-communication.md` 逐条可核对）：
   - 结构化 JSON 换自然语言正文：校正后总表口径——**准确率 62.3% vs 47.4%（+14.9pp）、错误减少 93%、token 下降 25.2%**（14 模型 8,560 试，arxiv 2607.03953）；
   - 致密序列格式（TOON/TRON）省 18–27% token，但准确率掉 9–14pp，多轮解析失败会级联放大（arxiv 2605.29676）——据此**放弃自定义紧凑 DSL**；
   - 生产级先例 `tap`（arxiv 2606.14445）验证了"文件为事实来源 + 环境各自实时通知"的双层结构，与本次实践同构；
   - 最终采纳：**信封（id/from/type/reply_to 等最小字段）+ 自然语言正文**。
3. **产出实物**：`scripts/msg.py` v0.3（stdlib 单文件）。一消息一 JSON 文件、临时写后原子 rename 发布；`ack`（处理完移入 done/）= 已读证据，与唤醒（tmux 铃声）分离。经 echo1 真实跨会话闭环验收：主流程与 7 项边界行为全部通过（含路径穿越拒绝、重复 ack 幂等）。
4. **邮箱定位（规范性结论）**：可选增强，非强制通道。需要回执的 ASK/ACK/ERROR、需要唤醒且正文长的走邮箱；日常 INFO、长推理只写日志；日志永远是事实来源（`conventions/messaging.md` v1.0）。设计动机：与 task1 建立的点名交棒打通，把"已读"从对话记忆变成文件证据。
