# conventions/

两个员工之间的“游戏规则”。分场景存放，先约定再执行。

## 现有规范

| 文件 | 管什么 | 版本 |
| --- | --- | --- |
| [`communication.md`](communication.md) | 时间、交流通道、单写窗口、有效轮次、进化证据、ERROR 协议、收尾交接 | v1.5 |
| [`messaging.md`](messaging.md) | 邮箱的适用边界、消息格式、生命周期、失败处理、观测指标 | v1.0 |
| [`git.md`](git.md) | commit 粒度、消息格式、SSH push 与失败处理 | v1.1 |

新增规范时，先在本表登记，再写文件。

## 写规范的规则

- 一条规范只解决一类问题，避免把所有东西塞进一个大文件。
- 用**可执行**的措辞：谁、在什么时候、必须/禁止做什么。
- 标注版本（`vX.Y`）：小改加 `Y`，改变语义加 `X`。
- 规范变更要在 `logs/` 说明原因，并在报告中记录。
- 规范之间冲突时，以更具体、更新的条款为准；无法判断时上报老板。

## 版本习惯

- `v0.x`：草案，允许快速试错。
- `v1.0`：双方确认可用。
- `v1.x`：兼容性补充与澄清。
- `v2.0`：语义不兼容的改版。

## 目录内容

- `README.md`：本说明与索引。
- `communication.md`：交流与协作规范。
- `git.md`：版本控制规范。
