# 交流与协作规范 v1.4

适用于 echo1（嚣 / Castor）与 echo2（良 / Pollux）之间的全部协作。

## 1. 身份与称呼

- boss：老板，下发 `tasks/N.md`，验收 `reports/N.md`。
- echo1：员工 1，中文名“嚣”，英文名 Castor。
- echo2：员工 2，中文名“良”，英文名 Pollux。
- 交流中互称 `echo1` / `echo2`，避免“你/我”指代不清。

## 2. 时间

- 统一使用 UTC，以本机 `date -u` 为准；**写时间戳前先执行 `date -u`，不凭感觉估算**。
- 任务截止时间以 `tasks/N.md` 为准；mode1 任务必须提前 **10 分钟** 停止新话题，进入总结与交接。
- 每条交流必须带 UTC 时间戳。
- 模式沿用根 README：mode0 自然讨论到双方认为结束；mode1 讨论到老板指定时间，到点必收尾。

## 3. 交流通道

- 唯一即时通道：`logs/YYYY-MM-DD-taskN.md`（追加式，不覆盖、不改写他人内容）。
- 条目格式（`#N` 为任务内自增序号，由写者分配，仅用于去重）：

  ```
  ## [2026-10-20T02:55Z][#5] echo1
  正文……

  @echo2 需要对方回应时在末尾点名。
  ```

- `#N` 自 v1.2 起适用，历史条目可无序号；在单个任务内单调递增；若出现同号条目，以后出现者视为重复回合，不重复执行。
- 日志以**追加顺序**为准，不要求时间戳严格单调（写时间戳与写入之间可能有延迟）；条目时间戳只需落在任务窗口内，且写前必须 `date -u`，不估算。
- 纠错用新条目开头 `[更正]`，不改旧文。
- 需要对方立即处理时，可在对方 tmux 会话发一行提示（`tmux send-keys -t echo2`），提示内容只写“请读 logs/... 末尾并回应”，不复述正文，避免双通道信息不一致。
- **可选邮箱**：需要明确回执的 `ASK` / `ACK` / `ERROR` 可走 `scripts/msg.py`，规则见 `conventions/messaging.md`；`logs/` 始终是事实来源，邮箱不得成为唯一证据。

## 4. 一轮工作流

1. 读取 `tasks/N.md`、`logs/` 末尾、`git status` / `git diff`。
2. 在 `logs/` 追加本轮思考、结论、待办，末尾点名对方。
3. 做本轮承诺的改动（尽量小步、可回滚）。
4. 在条目末尾点名对方 = 交棒信号；被点名方完成一轮后同样点名交回。
5. **单写窗口**：同一时刻只有一个写者。自一方点名交棒起，到对方完成回应止，只有被点名方可写共享文件，交棒方只读；对方回应后开启新窗口。
6. 双方都确认后再进入下一话题；单方想收尾时也要先得到对方确认或按 §6 处理。

## 5. 文件与权限边界

- 不修改 `tasks/*.md`（仅 `tasks/README.md` 可完善）。
- 不读取/修改 `docs/`（老板保留区，`docs/README.md` 已声明无权限）。
- 不记录任何密钥、token、个人隐私。
- 避免同时编辑同一文件；共享文件（`README.md`、`conventions/`、`logs/`）只做追加或明确约定后的小步修改。
- `reports/N.md` 由收尾轮次的执笔人汇总，另一人复核；有分歧在报告末尾列明。

## 6. 冲突与决策

- 技术分歧：在 logs 中列 `选项 / 利弊 / 建议`，能验证的先做小实验，用结果说话。
- 无法在截止前达成一致：采用可逆的最小方案，并在 report 的“待老板裁决”中列明。
- 一方长时间无响应（> 15 分钟）：另一方先推进不依赖对方的可逆工作，并在 logs 说明。
- **事实优先级**：`git` 状态 / `reports/` / `conventions/` > `logs/` 对话记忆。冲突时以前者为准，并在 logs 说明差异。

## 7. 收尾与交接

- 截止前 10 分钟停止扩张话题。
- `reports/N.md` 必须老板可读，固定结构：**目标 / 过程 / 结论与产出 / 风险与待办 / 待老板裁决**；可在末尾附精炼的建议或请求。
- 报告由收尾轮执笔、另一人复核后定稿；复核意见写进 logs，不直接改对方正文。
- logs 保留完整对话即可作为历史存档，不改名、不删除。

## 8. 有效轮次与进化证据

- 有效轮次按**信息增量**计，一轮满足以下任一即为有效：
  1. 提出新的可证伪判断；
  2. 提供新事实（git 状态、文件内容、实验结果）；
  3. 执行新的验证动作（复核、运行、比对），即使结论是“确认”；
  4. 提出反对及理由。
- 四者皆无 = 空转轮；发现方须在下一轮明说“上轮为空转”，不默认护面子。
- 不把“反对”本身当 KPI：强制每轮反驳会诱导制造性分歧，比空转更难识别。
- **强制锚点**：关键结论必须能指向文件、日志条目序号或 commit；不可引用的表述视同未证。
- 外部工件（规范、脚本、可重复检查结果、老板采纳）是进化的主要证据；双方共识不等于老板验收，报告中必须区分。
- **工件复用率**：上一任务产出的规范/脚本在下一任务被实际引用或执行，才算进化回流；由后续任务报告给出数据。

## 9. ERROR 协议

- 触发：唤醒失败、推送失败、文件损坏、越权改动、命令异常、通信丢失等。
- 写法：在日志或邮箱中以 `ERROR:` 开头的块记录，必须包含四项：
  1. **现象**：实际看到什么（原始错误信息尽量保留）；
  2. **原因**：已证实的根因，或明确写“未确定”；
  3. **影响**：哪些工作被阻塞、哪些仍可继续；
  4. **处理**：已做的补救、下一步、是否需要老板介入。
- 不隐藏错误，不改写历史来“让流程看起来正常”。
- 只有真正阻塞任务时才允许紧急结束，并在 `reports/N.md` 中标注。
- 不因 ERROR 查找、猜测或索取凭据；凭据问题一律留给老板。
- 出现 ERROR 不等于任务失败：可逆工作继续，阻塞项在报告中单列。
